ANSWER

프론트·백엔드·DB에서 각각 중복을 방지한다.

프론트에서는 저장 중 버튼을 비활성화하고, 백엔드에서는 요청 ID 또는 주문번호를 검증합니다. DB에는 Unique Constraint를 두어 마지막 방어선을 만듭니다. 서버가 여러 대라면 한 서버의 메모리만으로는 중복을 막을 수 없으므로 DB나 Redis 같은 공유 저장소가 필요합니다.

키워드 → 답변 매핑

Service 중복 검사Architecture업무 규칙 주문 중복 여부를 화면이 아니라 서버의 업무 로직에서 판단합니다.
Unique ConstraintDB동시성 두 요청이 거의 동시에 통과하더라도 DB가 중복 저장을 최종 차단합니다.
Redis·DB 공유 저장소분산 환경다중 서버 서버별 메모리가 아닌 공용 상태를 사용해 여러 서버에서도 동일하게 중복을 막습니다.

키워드 → 답변 매핑

비밀번호 해시 비교HashSecurity 원래 비밀번호를 복원하거나 평문으로 저장하지 않고 검증합니다.

UPDATE orders
SET status = 'READY_FOR_DELIVERY',
    version = version + 1
WHERE order_no = 'O1001'
  AND version = 3;

수정 요청에 version 값을 함께 보내고 현재 버전과 일치할 때만 수정한다.

UPDATE 건수가 0이면 누군가 먼저 수정한 것입니다. 이 경우 “다른 사용자가 먼저 수정했습니다”라고 안내하고 최신 데이터를 다시 불러옵니다. 이것이 대표적인 낙관적 락 방식입니다.

키워드 → 답변 매핑

버전 비교 방식이 동시성 문제와 어떻게 연결되는지 보여줍니다.

version 전달Optimistic Lock 사용자가 처음 읽은 데이터의 시점을 숫자로 함께 전달합니다.
WHERE version = 3Race Condition원자성 읽은 뒤 다른 수정이 없었을 때만 단일 UPDATE로 반영합니다.
version + 1상태 변경 수정이 성공할 때마다 새 버전을 만들어 다음 충돌을 감지합니다.
수정 건수 0 확인충돌 감지 현재 DB 버전이 달라졌다는 뜻이므로 덮어쓰지 않고 실패로 처리합니다.
최신 정보 재조회Consistency 사용자가 변경된 최신 상태를 확인하고 다시 판단하도록 합니다.

키워드 → 답변 매핑

주문 저장과 알림 발송을 분리하는 이유를 개념별로 풀어냅니다.

이벤트 발행 후 응답AsyncNon-blocking flow 메일 완료를 기다리지 않아 사용자 응답 시간을 줄입니다.

DLQDead Letter Queue 반복 실패한 메시지를 별도로 격리해 원인 분석과 수동 재처리를 가능하게 합니다.
