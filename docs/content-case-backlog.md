# Over the Code 콘텐츠 케이스 백로그

이 문서는 향후 추가할 개발·개선·운영·인프라 트랙의 실무형 케이스 후보를 보관한다.

서비스의 기본 방향은 기술 이름을 먼저 외우는 것이 아니라, 실제 상황에서 출발해 시스템의 흐름과 각 계층의 책임을 이해하는 것이다.

---

## 1. 트랙을 구분하는 기준

같은 소재도 학습 질문에 따라 다른 트랙이 될 수 있다.

| 트랙 | 핵심 질문 |
|---|---|
| 개발 | 이 요구사항을 처음부터 어떻게 시스템으로 만들까? |
| 개선 | 이미 있는 시스템에서 어디를 어떻게 바꿔야 할까? |
| 운영 | 이미 동작하는 시스템에서 왜 문제가 생겼고 어떻게 복구·예방할까? |
| 인프라 | 애플리케이션은 어디서 실행되고 요청·배포·저장·관측은 어떻게 연결될까? |

예를 들어 `대시보드 컬럼 추가`라는 소재는 다음처럼 나뉜다.

- 개발: 새로운 판매 현황 대시보드를 처음부터 설계한다.
- 개선: 기존 대시보드에 담당자 이메일 컬럼을 추가한다.
- 운영: 추가한 컬럼이 일부 사용자에게만 비어 있는 원인을 찾는다.

---

## 2. 공통 콘텐츠 설계 원칙

각 케이스는 가능하면 다음 흐름을 따른다.

1. 실제 업무 또는 장애 상황을 제시한다.
2. 관련된 시스템 지도를 보여준다.
3. 요청·응답·로그·데이터 등 관찰 가능한 증거를 제공한다.
4. 가능한 원인이나 변경 지점을 좁힌다.
5. 핵심 개념 하나를 먼저 이해한다.
6. 프론트엔드·백엔드·DB·인프라의 책임을 구분한다.
7. 해결 방법의 한계와 트레이드오프를 비교한다.
8. 학습자가 자기 말로 설명한 뒤 예시 답안과 비교한다.
9. 비슷한 다른 상황에 적용한다.

객관식만 반복하지 않고 트랙과 주제에 맞는 활동을 사용한다.

- 요청 경로에서 실패 지점 선택
- 정상·장애 설정 비교
- 로그와 메트릭으로 가설 제거
- 코드 또는 파일 변경 지점 찾기
- 데이터가 계층을 통과하는 순서 조립
- 안전한 배포 순서 조립
- 자기 말로 원인과 해결책 설명

---

# 개선 트랙

개선 트랙의 목표는 이미 있는 코드를 읽고 변경 범위를 찾아 안전하게 수정하는 것이다.

## 개선 01. 대시보드에 컬럼 하나 추가하기

**상황**

> 주문 대시보드에 `담당자 이메일` 컬럼을 추가해 주세요.

**따라갈 흐름**

```text
PostgreSQL
→ Repository
→ Service
→ Response DTO
→ JSON Response
→ Frontend API
→ State / Props
→ Table Component
```

**학습 개념**

- End-to-End 데이터 흐름
- Entity와 DTO의 차이
- 필드 매핑
- 변경 영향 범위
- 관심사의 분리

**추천 활동**

- 필드가 빠진 계층 찾기
- 변경해야 하는 파일을 순서대로 선택하기

---

## 개선 02. 주문 검색 조건 하나 추가하기

**상황**

> 주문 목록에서 `출고 예정일` 범위로 검색할 수 있게 해 주세요.

**따라갈 흐름**

```text
검색 UI
→ Query Parameter
→ Controller Request
→ Service 검색 조건
→ Repository Query
→ DB Index
```

**학습 개념**

- Query Parameter
- 선택 검색 조건
- 날짜 범위와 경계값
- `null`과 빈 값
- Index

---

## 개선 03. 주문 상태값 하나 추가하기

**상황**

> 주문 상태에 `출고 보류`를 추가해 주세요.

**확인할 변경 범위**

```text
DB 제약조건
→ Java Enum
→ 상태 전이 규칙
→ API 응답
→ 프론트 라벨
→ 검색 필터
→ 통계 집계
→ 테스트
```

**학습 개념**

- Enum
- 상태 전이
- 누락된 `switch`
- 하위 호환성
- 집계와 리포트 영향

---

## 개선 04. API 응답 필드 이름 변경하기

**상황**

> API의 `dealerName`을 `partnerName`으로 바꿔 주세요.

**학습 개념**

- API 계약
- Breaking Change
- Deprecated 필드
- 하위 호환성
- 점진적 마이그레이션
- 여러 클라이언트에 미치는 영향

**핵심 질문**

- 기존 필드를 즉시 제거해도 되는가?
- 구버전 웹·앱·외부 연동 시스템은 무엇을 사용하는가?
- 일정 기간 두 필드를 함께 제공해야 하는가?

---

## 개선 05. 필수 입력값 하나 추가하기

**상황**

> 주문 저장 시 `고객 연락처`를 필수로 받아 주세요.

**따라갈 흐름**

```text
프론트 입력 검증
→ Request DTO Validation
→ Service 업무 규칙
→ DB NOT NULL
→ 기존 데이터 마이그레이션
```

**학습 개념**

- 프론트 검증과 서버 검증의 차이
- Bean Validation
- `NOT NULL`
- 기존 데이터 처리
- 안전한 배포 순서

---

## 개선 06. 목록에 페이지네이션 추가하기

**상황**

> 주문이 10만 건으로 늘어나 전체 목록 조회가 느려졌습니다.

**학습 개념**

- Pagination
- Page와 Slice
- `LIMIT`과 `OFFSET`
- Cursor Pagination
- 안정적인 정렬 기준
- 전체 개수 조회 비용

---

## 개선 07. 외부 API 연동 필드 추가하기

**상황**

> 차량 정보를 외부 제조사 API에서 가져와 주문 화면에 표시해 주세요.

**학습 개념**

- 외부 API Client의 위치
- 외부 DTO와 내부 모델 분리
- Timeout
- 오류 변환
- Mock 테스트
- 외부 시스템 변경 격리

---

## 개선 08. 공통 버튼을 한 화면에서만 다르게 바꾸기

**상황**

> 공통 저장 버튼이지만 주문 화면에서만 문구와 동작을 다르게 바꿔 주세요.

**학습 개념**

- 공통 컴포넌트
- Props와 기본값
- 재사용성과 예외 처리
- 조건문이 계속 늘어날 때의 문제
- 공통 컴포넌트를 분리해야 하는 기준

---

# 개발 트랙

개발 트랙의 목표는 요구사항을 화면·API·업무 규칙·DB·운영 조건으로 번역하고 처음부터 설계하는 것이다.

## 개발 01. 주문 취소 기능 설계하기

**상황**

> 사용자가 확정된 주문을 취소할 수 있는 기능을 만들어 주세요.

**먼저 물어야 할 질문**

- 누가 취소할 수 있는가?
- 어느 상태에서 취소 가능한가?
- 결제가 완료된 경우 어떻게 하는가?
- 재고와 알림은 어떻게 처리하는가?
- 외부 시스템 실패 시 어디까지 되돌리는가?

**학습 개념**

- 상태 전이
- 인증과 인가
- 트랜잭션
- 외부 시스템 연동
- 보상 처리
- 감사 로그

---

## 개발 02. 대용량 엑셀 다운로드 기능 설계하기

**상황**

> 관리자가 검색한 주문을 엑셀 파일로 내려받을 수 있게 해 주세요.

**설계 질문**

- 최대 조회 건수는 얼마인가?
- 동기 다운로드로 충분한가?
- 파일 생성이 오래 걸리면 어떻게 알릴 것인가?
- 개인정보를 포함해도 되는가?
- 파일은 어디에 얼마나 보관할 것인가?

**학습 개념**

- Streaming
- 비동기 작업
- Object Storage
- 다운로드 권한
- 파일 만료
- 대용량 메모리 처리

---

## 개발 03. 관리자 승인 기능 설계하기

**상황**

> 일정 금액 이상의 주문은 관리자 승인을 받은 뒤 확정되도록 만들어 주세요.

**학습 개념**

- 승인 상태와 상태 전이
- 승인 권한
- 중복 승인 방지
- 승인·반려 이력
- 반려 후 재요청
- 동시 처리

---

## 개발 04. 알림 설정 기능 설계하기

**상황**

> 사용자가 주문 상태 변경 알림을 이메일·문자·푸시 중에서 선택하게 해 주세요.

**학습 개념**

- 사용자 수신 동의
- 이벤트 발행
- 채널별 Consumer
- 재시도와 DLQ
- 중복 발송 방지
- 발송 이력
- 느슨한 결합

---

## 개발 05. 판매 현황 대시보드 설계하기

**상황**

> 법인별·딜러별·모델별 판매 현황을 조회할 수 있는 대시보드를 만들어 주세요.

**설계 질문**

- 어떤 지표와 필터가 필요한가?
- 실시간 데이터여야 하는가?
- 원본 주문을 매번 집계할 것인가?
- 사전 집계가 필요하다면 갱신 주기는 얼마인가?
- 조회 권한은 어떻게 제한할 것인가?

**학습 개념**

- 요구사항을 데이터 모델로 변환하기
- 집계 API
- 사전 집계
- 조회 권한
- 캐시
- 데이터 최신성과 성능의 트레이드오프

---

# 운영 트랙

운영 트랙의 목표는 증상에서 출발해 증거를 확인하고 원인을 좁힌 뒤 복구와 재발 방지를 설계하는 것이다.

현재 구현된 운영 01~10 이후에 추가할 후보들이다.

## 운영 11. 성공 메시지는 떴는데 데이터가 사라졌습니다

**상황**

> 저장 완료 메시지가 표시됐지만 새로고침하니 데이터가 없습니다.

**확인 흐름**

```text
프론트 성공 처리
→ HTTP Status
→ 서버 예외 처리
→ Transaction
→ Commit / Rollback
```

**학습 개념**

- HTTP 성공과 업무 성공의 차이
- 예외를 삼키는 문제
- Transaction Rollback
- 낙관적 UI 업데이트
- 오류 응답 계약

---

## 운영 12. API에는 데이터가 있는데 화면에는 보이지 않습니다

**상황**

> 브라우저 Network 탭의 응답에는 데이터가 있지만 화면은 비어 있습니다.

**확인 흐름**

```text
API Response
→ Frontend API 함수
→ State
→ Props
→ Component
→ 조건부 렌더링
```

**학습 개념**

- 프론트엔드 데이터 흐름
- 필드명 불일치
- `null`과 `undefined`
- 비동기 상태
- 조건부 렌더링

---

## 운영 13. 일부 사용자에게 날짜가 하루 다르게 보입니다

**상황**

> 한국 사용자에게는 8월 2일인데 해외 사용자에게는 8월 1일로 표시됩니다.

**학습 개념**

- UTC
- Time Zone
- Timestamp
- 날짜와 시각의 차이
- 서버 저장 기준
- 브라우저 로컬 시간 변환

---

## 운영 14. 화면 합계와 정산 금액이 1원씩 다릅니다

**상황**

> 같은 주문 목록인데 프론트엔드 합계와 정산 시스템 합계가 일치하지 않습니다.

**학습 개념**

- 부동소수점
- `BigDecimal`
- 반올림 시점과 정책
- 프론트엔드와 백엔드 계산 중복
- 공식 계산 책임의 위치

---

## 운영 15. 다음 페이지에 주문이 중복해서 나타납니다

**상황**

> 목록의 다음 페이지로 이동했더니 앞 페이지에서 본 주문이 다시 보이거나 일부가 빠집니다.

**학습 개념**

- Pagination
- 정렬 기준
- 동일 정렬값
- 조회 중 데이터 변경
- Offset과 Cursor 방식
- 안정적인 정렬

---

## 운영 16. DB에는 값이 있는데 API에서는 `null`입니다

**상황**

> DB에는 담당자 정보가 있지만 API 응답의 담당자는 `null`입니다.

**확인 흐름**

```text
DB Row
→ JOIN
→ Entity
→ Projection
→ DTO Mapping
→ JSON Serialization
```

**학습 개념**

- JOIN 조건
- Lazy Loading
- Projection
- DTO 매핑 누락
- JSON 직렬화

---

## 운영 17. 업데이트하지 않은 앱에서만 오류가 발생합니다

**상황**

> 웹과 최신 앱은 정상인데 구버전 모바일 앱에서만 API 오류가 발생합니다.

**학습 개념**

- API 하위 호환성
- 필드 추가와 제거
- API Versioning
- 다중 클라이언트
- 배포 순서
- Contract Test

---

## 운영 18. 배포 중 일부 요청이 500 오류로 실패합니다

**상황**

> 새 버전을 배포하는 몇 분 동안 일부 요청만 실패합니다.

**학습 개념**

- Rolling Deployment
- 구버전과 신버전 공존
- DB Migration 순서
- Readiness Probe
- Graceful Shutdown
- Zero-Downtime Deployment

---

## 운영 19. 배치가 1만 건 중 6천 건만 처리했습니다

**상황**

> 정산 배치가 중간에 실패해 일부 주문만 반영되었습니다.

**학습 개념**

- 부분 실패
- Checkpoint
- 재시작과 재처리
- 멱등성
- 처리 상태
- 실패 데이터 격리

---

## 운영 20. 결제 Webhook 때문에 배송이 두 번 시작됐습니다

**상황**

> 결제 완료 Webhook이 같은 이벤트를 여러 번 보내 배송 요청도 중복 생성됐습니다.

**학습 개념**

- At-least-once Delivery
- 중복 이벤트
- Event ID
- 멱등한 Consumer
- 재시도
- 순서가 바뀐 이벤트

---

## 운영 21. 수정한 주문이 검색 결과에는 예전 값으로 보입니다

**상황**

> 주문 상세는 최신 값인데 검색 결과는 이전 값을 반환합니다.

**학습 개념**

- 검색 인덱스
- 비동기 동기화
- Eventual Consistency

# 인프라 트랙

인프라 트랙의 목표는 클라우드 제품명을 외우는 것이 아니라, 애플리케이션의 요청·실행·저장·배포·관측 경로를 이해하는 것이다.

## 인프라의 기본 시스템 지도

```text
사용자
  ↓
DNS
  ↓
CDN
  ↓
Load Balancer
  ↓
Application Server / Container
  ├── Redis
  ├── Queue → Worker
  ├── Object Storage
  └── PostgreSQL

전체 구간
  └── Log / Metric / Trace
```

먼저 일반 역할을 배우고 실제 서비스 이름은 예시로 연결한다.

| 역할 | 일반 개념 | AWS 예시 |
|---|---|---|
| 도메인을 주소로 변환 | DNS | Route 53 |
| 정적 파일을 가까운 곳에서 전달 | CDN | CloudFront |
| 요청을 여러 서버에 분배 | Load Balancer | ALB |
| 애플리케이션 실행 | Compute | EC2, ECS |
| 파일 저장 | Object Storage | S3 |
| 관계형 데이터 저장 | RDBMS | RDS |
| 비밀정보 저장 | Secret Store | Secrets Manager |
| 로그와 메트릭 수집 | Observability | CloudWatch |

## 3. 추천 제작 우선순위

### 1차: 현재 앱 구조와 직접 연결되는 케이스

1. 개선 — 대시보드에 컬럼 하나 추가하기
2. 운영 — API에는 데이터가 있는데 화면에는 보이지 않기
3. 개선 — 주문 검색 조건 하나 추가하기
4. 운영 — DB에는 값이 있는데 API에서는 `null`
5. 개선 — 필수 입력값 추가와 기존 데이터 마이그레이션

### 2차: 실무에서 자주 발생하는 데이터·호환성 문제

1. 운영 — 날짜가 사용자별로 다르게 표시됨
2. 운영 — 금액 합계가 1원씩 다름
3. 개선 — 상태값 추가
4. 운영 — 구버전 클라이언트만 오류 발생
5. 운영 — 배치가 중간에 실패해 일부만 처리됨

### 3차: 인프라 골격을 만드는 다섯 케이스

1. 도메인은 열리는데 API 서버에 연결되지 않음
2. 서버는 켜져 있는데 애플리케이션이 응답하지 않음
3. 서버를 두 대로 늘리자 로그인이 풀림
4. 재배포하자 업로드 파일이 사라짐
5. 배포 중 서비스가 중단됨

이 다섯 케이스를 통해 다음 기본 지도를 먼저 만든다.

```text
사용자의 요청이 어디로 들어오는가
→ 애플리케이션이 어디서 실행되는가
→ 여러 서버는 어떻게 연결되는가
→ 데이터와 파일은 어디에 남는가
→ 새 버전은 어떻게 교체되는가
```

## 4. 연결형 시리즈 아이디어

같은 소재를 여러 트랙에서 이어서 학습하면 계층과 역할 차이를 자연스럽게 반복할 수 있다.

### 대시보드 필드 시리즈

```text
개발
판매 현황 대시보드를 처음부터 설계한다

개선
기존 대시보드에 담당자 이메일 컬럼을 추가한다

운영 1
API에는 담당자가 있는데 화면에는 보이지 않는다

운영 2
DB에는 담당자가 있는데 API에서는 null이다

인프라
배포 후 구버전과 신버전이 섞여 일부 요청만 실패한다
```

### 로그인 시리즈

```text
개발
로그인과 권한 구조를 설계한다

운영
로그인에 성공했는데 다음 화면에서 로그아웃된다

인프라
서버를 두 대로 늘리자 로그인이 간헐적으로 풀린다
```

### 파일 처리 시리즈

```text
개발
대용량 엑셀 다운로드를 설계한다

운영
대용량 엑셀 업로드 후 서버가 멈춘다

인프라
재배포 후 업로드 파일이 사라진다
```

이 방식은 동일한 소재를 반복하는 것이 아니라, 하나의 시스템을 요구사항·코드 변경·장애·실행 환경이라는 서로 다른 관점에서 바라보게 한다.
